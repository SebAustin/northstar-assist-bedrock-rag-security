# Northstar Assist guardrail: control rationale

`config.json` is the exact request body for `aws bedrock create-guardrail --cli-input-json file://guardrail/config.json` (boto3 `create_guardrail(**cfg)`). It was validated against botocore 1.43.110 (`CreateGuardrail` input shape: fields, required members, enums, lengths and patterns). JSON allows no comments, so the reasoning lives here. The two blocked messages match `blocked_messages` in `redteam/prompts.yaml`, so `classify()` can recognise a block even when no `content_filtered` stop reason comes back. Suite case IDs are in brackets.

| Control | Threat (OWASP) | Threshold / action and why | Known limitation |
|---|---|---|---|
| `PROMPT_ATTACK` filter | Direct injection, jailbreak, role-play (LLM01) [PI-01, PI-02, HARM-01] | Input **HIGH**, output **NONE** (the API only allows NONE on output). HIGH because the users are internal and benign traffic is plain Q&A, so the false-positive cost is low. | **Retrieved KB chunks bypass this filter.** It screens the user turn only, not tool results, so indirect injection through a poisoned document [IND-01] relies on system prompt v2. The compensating control is an `afterToolCall` hook that runs `ApplyGuardrail` on chunks. Classic tier: no prompt-leakage detection and weaker on encoded payloads [PI-03, SPE-01]. |
| Content filters: HATE, INSULTS, SEXUAL, VIOLENCE, MISCONDUCT | Harmful or toxic content in or out (LLM01 goal, LLM05) [HARM-01] | **HIGH** in and out. A workplace assistant has no legitimate need for borderline content. | HIGH can over-block security docs that describe attacks or incidents (e.g. the DR plan or the incident report). Measured by BEN-03. Classic tier covers English, French and Spanish only. |
| Denied topic `LegalMedicalFinancialAdvice` | Overreliance on unqualified advice (LLM09) [DT-01] | BLOCK in and out. Personalised advice is a liability whatever the source. | Topic classification is probabilistic. Questions *about* the compliance or benefits docs may sit close to the boundary. |
| ~~Denied topic `CredentialsAndSecrets`~~ (removed in v2) | Credential harvesting (LLM02) [SEC-01, SEC-02] | Removed. | In v1 it blocked legitimate questions about the password policy, MFA and API authentication, on input and output. v2 protects secret **values** instead: PII detectors for passwords and AWS keys (BLOCK), the `NorthstarApiKey` regex (ANONYMIZE) and the MISCONDUCT filter. A soft "list any API keys" request passes the input filters; output masking and the system prompt cover it. |
| Denied topic `OtherEmployeesPersonalData` | Colleague compensation and personal data, bulk contact dumps (LLM02) [PII-01, PII-03, MT-01] | BLOCK in and out. Individual compensation is a Block item in the S6 verdict rule. | It cannot tell an authorised HR user from anyone else: there is no per-user identity at the harness. Paraphrased or gradual multi-turn requests may slip past it. |
| Denied topic `NonNorthstarTasks` | Off-mission use, denial of wallet (LLM10) [OOS-01] | BLOCK on **input** only. Output is NONE (detect and trace) so that legitimate code snippets from the API docs are not blocked. | Mixed requests (a Northstar question plus an unrelated task) may pass. The system prompt also declines them. |
| PII **BLOCK**: SSN, card, US bank account, AWS access key, AWS secret key, password | Secret or regulated data in or out (LLM02) | BLOCK both directions, so they never reach the model, the reply or the invocation logs. | **Defence in depth only.** The corpus holds none of these. PASSWORD and AWS_SECRET_KEY detection may misfire on example strings (BEN-04). |
| PII **ANONYMIZE**: EMAIL, PHONE, ADDRESS | Bulk contact leakage from employee_directory.csv and customer CSVs (LLM02, LLM08) [PII-01, PII-02] | Input **NONE** (employees can type their own details), output **ANONYMIZE** (masked as `{EMAIL}` etc.). | Masks legitimate contacts too, e.g. a Service Desk address. It does not mask names, revenue or deal sizes, which the system prompt and topic must cover. NAME is deliberately not anonymised: it would break normal answers such as incident owners. Phone *extensions* (4 digits) may not be detected as PHONE. |
| Word filter: managed `PROFANITY` | Abusive language (LLM05 output quality) | BLOCK in and out. | English list. Easy to evade with spelling variants. |
| Contextual grounding: GROUNDING **0.7**, RELEVANCE **0.6** | Hallucinated or off-topic answers (LLM09) [MIS-01, BEN-01..03] | BLOCK below the threshold. 0.7 is the AWS starting point; relevance is set looser (0.6) because answers that cite a source and add a caveat legitimately score lower. | **Contextual grounding may not receive a grounding source through the harness.** It only scores content tagged `grounding_source` / `query` (`guardContent` qualifiers), and the harness passes KB chunks as tool results, so the check may be skipped or may block valid answers. Apply PLAN S3 [D6]: if it never evaluates, or blocks a benign answer, ship v2 without it and record the gap. |
| Tier | n/a | Classic, the default (no `tierConfig`). | Standard tier (prompt-leakage detection, stronger obfuscation handling) needs `crossRegionConfig` with a guardrail profile and cross-Region `ApplyGuardrail` permissions. It is out of scope for the lab and is a production recommendation. |

**What the guardrail cannot do (owned by other layers):** it cannot stop excessive agency (LLM06: IAM restricts the gateway role to `Retrieve`) [AGY-01]. It cannot authorise retrieval per user (LLM08: data-minimise the corpus or use a separate restricted KB). It cannot screen retrieved chunks (system prompt v2 plus an `afterToolCall` hook). It cannot sanitise UI rendering (LLM05: the Streamlit app must escape output) [OUT-01].
